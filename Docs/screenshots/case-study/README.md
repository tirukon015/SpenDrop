# SpenDrop case-study screenshot set

Captured 2026-09-25 on a freshly created **iPhone 17 Simulator (iOS 27.0)**, all at **1206 × 2622 px**, light appearance, using the production build of the app (`com.spendrop.SpenDrop`, version 1.3.0). Every frame is the real UI running the real OCR, parser, duplicate-detection and persistence code. Nothing was mocked, retouched or annotated.

## Privacy

- All expense rows come from the app's built-in synthetic sample data (`Data/SampleData.swift`) plus one synthetic transaction described below.
- The payment screenshot fed to OCR was rendered by a script (`capture-hooks.patch` documents the flow) and contains only fictional text: *Touch 'n Go eWallet / Payment Successful / RM18.50 / Paid to: McDonald's / 16 Sep 2026 9:42 PM / Ref No: TNG992837194 / Panasonic Air Conditioner RM450 Shop now*. It is checked in as `SpenDrop/Resources/DiagnosticSamples/sample_screenshot.png`.
- The receipt fed to OCR in screenshot 04 is also synthetic (`sample_photo.jpg`, "Mamak Corner Restoran", total RM 19.08, marked "Synthetic sample for testing" on the image).
- PayBook names and masked account numbers are the app's hard-coded sample contacts. No real person, account, phone number, token or credential appears in any file here.

## Notes on what the frames actually show

- **A. Share Sheet (02).** macOS accessibility automation is not granted to scripts on this machine, so the Photos app could not be driven. The sheet was opened by the app itself through `UIActivityViewController` on the synthetic image. The share row, including SpenDrop's extension, is the genuine iOS sheet; the item preview at the top is the generic placeholder iOS shows for an in-memory image.
- **B. Extension review (03).** The extension's `ShareExtensionView` and view model were hosted inside the main app for capture (the only source change was adding the two extension files to the app target temporarily). The OCR, parser, duplicate check and save path are the same code the extension runs. One observed parser result: the time was resolved to **9:42 AM** although the image says 9:42 PM. The AM/PM token was not carried through in this capture; it is recorded here rather than corrected.
- **C. Candidate amounts (04).** The "POSSIBLE AMOUNTS" row is a horizontal scroller in candidate order, so the first visible chips are line items; the selected RM 19.08 chip is further right. Earlier, with a column-aligned receipt (label and amount far apart), Vision returned "TOTAL" and "RM 19.08" as separate observations, the total lost its label, a line item won, and the app correctly downgraded to "Possible Expense Detected". That is a real parser limitation and is listed in the main documentation.

## How the captures were produced

1. Synthetic images rendered with AppKit scripts and checked in as the app's diagnostic samples (replacing files that had contained real data).
2. A temporary, local-only set of launch-argument hooks was applied to the sources (`--demo-review <sample>`, `--demo-share <sample>`, `--demo-autosave`, `--demo-duplicate-alert`, `--open-selftest`, `--demo-sharesheet <sample>`), following the pattern of the existing `--demo-duplicate` and `--open-detail` hooks. The full diff is in `capture-hooks.patch`.
3. Frames were taken with `xcrun simctl io <device> screenshot` after each launch.
4. The hooks were reverted. The production tree was rebuilt and the 48-case suite re-run (48/48) before these files were committed.

To reproduce: `git apply docs/screenshots/case-study/capture-hooks.patch`, build for a simulator, launch with the arguments above, then `git checkout -- .` to discard the hooks.
